# WORKFLOW — 個人開発向けAI駆動開発の共通運用

> この既存ゲームrepoに導入する共通運用規則。対象repoの固有権限は[PROJECT](PROJECT.md)と既存規約を優先。これは無人エージェント・無人同期・repo作成・PR・マージを自動で実行するプログラムではない。

## 0. 役割と資料の責務

- **ユーザー**：作りたい体験、重要な仕様・優先順位・公開方針と操作範囲を承認する。
- **相談AI（ChatGPT等）**：要件の壁打ち、GitHub自発再取得、短期メモ記録、正式仕様への反映案、Work Item・Codex依頼文、実差分レビューと次の一手を管理する。
- **実装AI（Codex等）**：明示された範囲の実装・テスト・commit・専用ブランチpush。使えない操作は実施したと装わない。
- **GitHub**：コード・正式仕様・メモ・履歴・Issue・PRの共有基盤。ChatGPTプロジェクト指示とチャット記憶は正本ではない。

**資料の入口は [docs/README](README.md)**。本repoでは採用済みゲーム仕様の正本が `docs/features/*.md` に分割済み。`docs/SPEC.md` は参照索引とし、既存規約 `docs/development-workflow.md` の命名・素材保護・Pages公開・より厳しい操作規制を維持する。原則は **短いAGENTS → 資料索引 → PROJECT＋status → Issue索引＋MEMO → 必要な正式仕様とコード**。

| 保存先 | 正本として管理すること |
|---|---|
| `AGENTS.md` | AI向けに、読む順序と参照先だけ |
| `docs/README.md` | 資料の地図、機能別正本の所有者、状態軸 |
| `docs/PROJECT.md` | プロジェクト固有設定・書込権限・導入段階 |
| `docs/WORKFLOW.md` | このプロジェクトの開発・GitHub・メモの操作ルール |
| 固定Inbox Issue本文 | **未処理メモの索引だけ**（ID・状態・概要・リンク） |
| 単一 `docs/MEMO.md` | **未反映の決定・変更・撤回・保留の本体** |
| `docs/SPEC.md` → 必要時 `docs/features/*.md` | **採用済み仕様の正本**。機能ごとに1箇所 |
| `docs/status.md` | **今の進捗、未確認、次の一手**。作業日誌にしない |
| Work Item Issue／PR | 実行タスク・受入条件／変更差分・検証 |
| `docs/history/`、`docs/production/`、`docs/architecture.md` | 履歴、素材制作、構成説明。必要になった場合だけ |

## 1. 「こういうアプリ作りたい」からの立ち上げ

**初回の依頼は目的・体験の一言で足りる。** ユーザーに最初からGitHub URL・技術・予算・設計書の入力を強制しない。まだChatGPTプロジェクトやrepoがない場合も相談を開始できる。

1. **構想の整理（相談AI）**：何を作りたいか、最初に確かめたい体験、MVP／PoCの境界を短く整理。技術・費用は候補として提示し、未承認の重要要件を勝手に確定しない。必要な情報だけ自然に聞く。
2. **新規／既存の判定（相談AI）**：ユーザーから既存repoのURLがあるか確認。既存ならmain・README・AGENTS・docs・PR・ブランチ・公開設定と未マージ／未コミット成果を保護調査する。新規ならrepo名、公開範囲、README、最小構成を提案し、repoの作成方法を案内。
3. **テンプレートの実態確認（相談AI）**：共通テンプレートのルートの配布物とGitHubの `is_template` 設定を実確認。有効なら「Use this template」で**デフォルトブランチ（main）のみを複製し、「Include all branches」を選択しない**よう案内。管理用の旧作業ブランチは新規repoへ持ち込まない。未設定／利用不可なら、ユーザーのrepo作成と承認されたファイル導入を案内し、実行済みと装わない。
4. **リポジトリ作成（ユーザー／利用可能なツール）**：新規repo作成は**名称・公開範囲・作成先を確認して明示承認後**。利用可能な接続に作成機能がなければユーザーにGitHub UIで作成してもらい、URLを受け取る。**「作成された」と推測しない**。既存repoは新しく作り直さず、そのまま保護。
5. **スターター導入案（相談AI）**：専用ブランチで配布ファイルだけを導入する計画を提示。既存README・AGENTS・仕様・PR・ソース・素材を無断上書きしない。複製された初期READMEは、作成するアプリの概要・起動方法を記したREADMEに置き換える。機能別正本・history・素材管理は必要になった段階で追加。
6. **指示文生成と設定（相談AI→ユーザー）**：リポジトリ直下の [共通テンプレートの指示文生成用プロンプト](https://github.com/elizabeeeth555/ai-dev-template/blob/main/PROJECT_INSTRUCTION_GENERATOR_PROMPT.md)（初期導入後は削除候補）の規則で、**このプロジェクト固有のChatGPT指示文の完成版**を作る。ユーザーがChatGPTプロジェクトを作成／既存のものを選択し、指示文を貼る。まだrepo未作成なら暫定指示文を作り、repo決定後に更新する。
7. **導入の承認と準備（ユーザー＋AI）**：対象repo・ファイル・ブランチ・許可操作を示して承認を取り、実際のスターターを安全に導入。commit・push後にGitHub上の差分とSHAを照合。PR作成／マージは別承認。
8. **固定Inbox設定と引継ぎ（ユーザー＋相談AI）**：許可を得て固定Issueを**1件だけ**作成、Issue番号とメモ書込先ブランチをPROJECTに設定。Issue本文の索引と単一MEMOを紐付け。確認できた既存の承認を正本・メモへ分類。既存のメモコメントがあれば履歴として保護。
9. **運用開始（相談AI）**：初期化したPROJECT・SPEC・status・READMEが**mainに反映済みか、未マージならどのブランチ／SHAにあるか**を実確認して記録。正本・メモ・Issue・権限を実際に取得でき、参照先の整合と未マージ状態が把握できたら `active` とする。**細かな独立異常系試験を開始条件にしない**。実開発の中で問題を直す。

**順序は依存関係に合わせて柔軟に**：ChatGPTプロジェクトを先に作る場合、既存repoへ導入する場合などは前後してよい。ただしrepo作成、書込、PR、マージ、公開は決して承認を飛ばさない。取得できない情報は「未確認」と明記。作業できないツールに無理に依存しない。

## 2. 日常の壁打ち・自発再取得

- 開始・再開、重要な話題転換、仕様の採用・変更・撤回、Codex依頼、正本更新、レビュー・マージ判断前に、相談AI自身がGitHubから必要な資料と未処理事項を取得する。長い壁打ちは**10〜15往復程度を参考**にするが厳密な回数管理や常駐監視は不要。
- ユーザーが深掘りしたい時は、元の目標との関係を把握しつつ深掘りする。目的・優先順位・設計粒度が本当に変わったら明示的な新決定として扱い、旧判断を黙って消さない。
- **重要操作前の取得失敗**、正本とメモ・コードの矛盾、未マージ成果・権限の不明はその操作を停止。調査と差分案は継続できる。無指示で取得できると保証された機能があるとは言わない。
- ユーザーには「目的・何が決まったか・重要な未決・次の一手」を必要な時だけ簡潔に伝える。過剰な進捗レポートや毎回の全資料読込は不要。

## 3. 固定Issue索引＋単一MEMO

**短期記憶は `docs/MEMO.md` 1ファイル**。固定Issue本文は、そのMarkdownへのID別リンクを持つ索引。新規メモ用にコメント・別Issue・別Markdownを作らない。移行前のIssueコメントは履歴として保護する。

- 重要な決定、暫定案、変更・撤回、保留や引継ぎに必要な内容を**意味のある節目**で記録。最小要素はID＋件名／採否と同期状態／要点／日付と判断根拠。変更元、部分置換の条件、反映先・SHA、次の確認は必要時だけ。
- **採否**：`confirmed / tentative / needs-decision / rejected`。**同期状態**：`pending / branch-ready / reflected / withdrawn`。採用済みでも未マージなら反映済みではない。
- 既存confirmedの一部変更は**旧IDと変更条件・理由を参照する新ID**で扱い、影響しない旧条件を維持。新しいtentativeで旧confirmedを上書きしない。
- **運用ブランチをPROJECTに特定**。mainへのメモ直接pushは当該repoで個別に明示許可された場合だけ。無許可なら単一の専用メモブランチなどを使い、他の機能開発ブランチと不用意に混ぜない。並行書込を前提にしない。
- **書込順**：最新MEMOのblob SHA・Issue本文・対象正本・関連ブランチ（必要なら旧コメント）を再取得→ID重複・承認・差分を確認→MEMOをSHA条件付きで更新→MEMOを再取得→Issue本文の索引を再構築して更新→Issueを再取得。索引はID・状態・短い件名・メモURLだけ。参照が作業ブランチなら明示し、mainへ統合後にURLを更新。
- **保存失敗の復旧**：MEMO保存失敗なら索引を更新しない。MEMO成功／索引失敗なら最新MEMOを正として索引を再生成。未知ID・競合・古いSHAなら停止して取得し直す。GitHub Issue本文の更新はファイルのblob SHAのような排他条件ではないため、単一ライターで直列運用する。
- **消し込み**：mainの正式仕様（またはユーザーが事前に承認した継続管理先）へ**内容・根拠・残課題を移管済みと実確認**したIDの節だけMEMOから削除し、その後Issue索引から除外する。Git履歴と旧コメントは保持。ブランチに書いただけでは削除しない。正本反映済み／削除失敗なら、正本を再取得して削除のみ再試行する。
- メモ記録が承認されていても、**正式仕様の採用や他リポジトリの書込権限を自動付与しない**。パス・書込担当・権限が未設定の間は会話内で整理し、保存済みと装わない。秘密情報をIssueやMEMOに保存しない。

## 4. 正本・現状・履歴の更新

- 最初は `docs/SPEC.md` だけを仕様正本にする。独立した責務が増えた時だけ `docs/features/*.md` に分割し、`docs/README.md` で所有者を示す。**既存仕様の重複コピーは作らず、旧節をリンクへ置換する**。
- 新しい判断を正本へ反映する前に、採用根拠、既存仕様・影響範囲・旧決定、実コード・未マージ差分を照合。明確でない部分を推測で採用しない。承認済み変更でもGit書込は許可された範囲のみ。
- `docs/status.md` は**進捗の最新スナップショット**。今の目的、確認したブランチ・PR／SHA、実装・テスト・公開の違い、未完了、次の一手のみ。完了済み作業の長い報告を追記しない。根拠はPR・Issue・Git履歴へ。
- `docs/history/`・`docs/production/`・`docs/assets/` は必要な時だけ。旧資料を削除する前に固有情報と参照元を照合し、移管先を明示。素材は候補／承認／原本登録／配信用変換／実装を区別し、権利・秘密・公開範囲を確認する。
- 文書更新とアプリ実装は同一ではない。仕様採用、ブランチ反映、CI、自動テスト、人間の受入、mainマージ、配信確認は**別々に報告**する。

## 5. 標準の開発8工程

1. **壁打ち・メモ**：重要な決定／変更／保留をMEMOへ記録しIssue索引を同期する。
2. **正本更新・作業定義**：決定済み仕様を正本と照合し、許可されたブランチへ反映。実装対象があれば必要な場合だけWork Item Issueを作り、`goal / done_when / source / status` と仕様パス・SHA・非対象を明確にする。
3. **Codex依頼**：相談AIが短い依頼文を作り、ユーザーがCodex等へ**手動で渡す**。利用できない自動連携を実行済みとしない。
4. **実装とpush**：実装AIが最新main・未マージ・未追跡差分を保護確認。許可された範囲だけを実装・テストし、指定の専用ブランチにcommit・push。失敗／未実施も明示。
5. **CI**：既存のビルド・Lint・型・自動テストを実行・確認。CI成功と実機成功を混同しない。PoCや小修正は必要な検証だけ。
6. **独立レビュー**：相談AIがGitHub上の実差分、関連正本、Work Item、CI、未マージ成果、公開への影響を確認。第三者AIレビューは有用な場合に追加、未実施なら未実施と記録。
7. **PR作成（別承認）**：対象ブランチ・HEAD・差分・検証結果をユーザーへ提示し、明示許可が出てからPRを作る。
8. **マージ（別承認）**：最新mainとPR HEAD、競合・CI・公開連動を再確認し、ユーザーが対象PRを明示承認してからマージ。**mainに正本が反映された後**に対応MEMOをID単位で消し込み、statusを最新化。デプロイ・公開は別承認（マージが自動公開を伴う場合はその効果を事前説明）。

**Work Itemは実行すべき仕事だけ**。壁打ちや短い小修正のために毎回作らない。Quick（小修正）／Explore（PoC・研究）／Standard（通常変更）を使い分ける。データ消失・課金・認証・公開等の危険操作にはどの方式でも**Protectedの追加確認**を行う。

## 6. Git・PR・ブランチ・公開の保護

- 作業前に最新リモートmain、関連ブランチ、既存PR、未コミット／未追跡ファイル、操作権限、mainマージ時の自動公開を確認。Web経由でローカル状態を確認できないなら、その旨を報告し他作業を破壊しない。
- **1作業目的／1ブランチが原則**。同じWork Itemの追加修正はマージまで同一ブランチ。元からあるブランチ・成果は保護する。差分衝突があれば停止。必要なら独立worktreeを使い、無断stash・reset・force push・対象外commitをしない。
- **意味を変えない**誤字・書式・説明リンク修正のmain直接編集は、そのrepoで**明示された例外許可と当該作業の許可が両方ある場合だけ**。仕様・コード・権限・公開挙動を変える修正は専用ブランチ。
- PR作成、PRクローズ、マージ、main直接push、デプロイ・公開、ブランチ削除は**それぞれ別の明示許可**。通常のブランチcommit/pushは、PROJECTと今回の作業依頼で許可された範囲に限る。
- マージ後の作業ブランチは**原則削除候補**。削除するなら最終レビューで対象ブランチと削除方針を明示し、対象を特定した承認を取得。PRマージ・main反映、対象HEAD不変、未統合の独自成果なし、他の作業・PR参照なし、default/protectedでないことを再確認してから。squash/rebase時はPR差分も確認し、ahead数だけで判断しない。未統合・研究・バックアップ・長期メモブランチ等は自動削除しない。
- mainへの反映がGitHub Pagesなどを自動公開する場合、**マージ承認時にその公開影響を明示**。デプロイ作業の承認や公開確認を省略してよいという意味ではない。
- できない操作はユーザーまたは担当AIの手動手順として案内し、実施済みと装わない。

## 7. 中断・再開・実運用改善

- 再開時：AGENTS→資料索引→PROJECT／status→固定Issue／MEMO→関連正本・Work Item・PRを**実際に再取得**。前回の会話だけで完了・採用と断言しない。
- 中断時：最新状態と次の一手をstatusか関連Work Itemへ短く残す。新しい引継ぎ文書を毎回増やさない。
- 改善点が見つかったら、発生した問題・実際の影響・変更案をMEMOへ記録し、共通運用の修正とアプリ固有の仕様変更を混同しない。無用な独立試験・大量の証跡保存は原則増やさない。
- **この文書だけで自動的に行われないもの**：会話外での常時監視・無人GitHub同期・repoの自動生成・無断PR／マージ・複数AIの排他制御。利用可能なツールと権限を毎回確認する。
