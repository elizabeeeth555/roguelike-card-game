対象：『継世の王座』／リポジトリ `elizabeeeth555/roguelike-card-game`。
制定日：2026-11-10（日本時間）。最終改訂日：2026-11-11（日本時間）。**ユーザー指定の運用規則として確定**。本書が運用・命名の正本であり、自動強制ツールの導入を意味しない。
仕様の優先順位・仕様状態と実装状態の定義は[設計資料入口](README.md)を参照する。過去のブランチ名やコミットをこの規約に合わせて書き換えない。

## 1. ブランチ運用

- `main`を安定版・公開版として維持する。mainへの直接pushは原則禁止。例外はその依頼でユーザーが明示承認した場合だけ。
- 作業開始時にstatus、現在のブランチ／HEAD、未コミット・未追跡ファイル、ローカル／リモートの差、関連PR、公開方式を確認する。
- 原則として**取得・確認した最新リモートmain**から専用ブランチを作る。ローカルmainが最新とは限らない。`origin/main`等の追跡参照もfetch前は古い可能性がある。
- 1ブランチ・1PRにつき1つの明確な目的。機能実装、ロジック調整、UI改修、研究の境界を意識し、ゲームロジック変更とUI改修は原則別PRにする。
- ブランチ作成や切替が既存差分と衝突する場合は停止して報告する。未追跡ファイルを上書きする切替、勝手なstash、削除、`reset --hard`、強制pushで解消しない。
- マージ済みブランチはmainへの反映と独自成果の有無を確認して**削除候補**にする。候補という分類は削除の承認ではない。
- 未マージ成果、研究作業、用途不明ブランチを勝手に削除しない。用途不明なら履歴・対応PR・mainとの差を調べる。
- 作業開始・レビュー・作業終了／中断の節目で棚卸しを更新する。長期中断時は目的、最新SHA、PR、未反映成果、次の判断を残す。長期間放置せず、削除と継続を区別する。
- 既存PRのクローズ／マージ、ブランチ削除／リネームは個別の明示承認を必要とする。

確認時の例（切替は依頼で許可され、安全を確認した場合だけ）：

```bash
git status --short --untracked-files=all
git branch -avv
git fetch origin
# fetch対象がmain限定の環境もあるため、必要な参照を取得できたか確認する
git log -1 origin/main
git switch --no-track -c chore/repository-workflow origin/main
```

fetchはリモートの内容を取得する操作であり、リモートへのpushや既存作業のマージではない。新規作業ブランチをorigin/mainの追跡ブランチにせず、初回pushが承認された時点で同名の作業ブランチをpush先・追跡先として明示する。

## 2. ブランチ命名

形式：`種類/対象-作業内容`。英小文字・数字・ハイフンを基本とし、短く具体的にする。スラッシュは種類と名前を区切る。

| 種類 | 用途 | 例 |
|---|---|---|
| `feat/` | 新機能 | `feat/studio-foundation` |
| `fix/` | 不具合修正 | `fix/ui-skill-tooltip` |
| `refactor/` | 外部動作を変えない内部整理 | `refactor/ui-config-foundation` |
| `docs/` | ドキュメント | `docs/combat-status-rules` |
| `test/` | テスト | `test/studio-json-compatibility` |
| `chore/` | 開発環境・運用 | `chore/repository-workflow` |
| `research/` | 独立検証 | `research/defense-skill-balance` |

王座工房の例：`feat/studio-ui-editor`、`feat/studio-fx-editor`、`feat/studio-story-editor`。
`work`、`test2`など目的を表さない**新規**名は禁止。既存`ui/`ブランチや`work`は棚卸し対象として保持し、本作業で一括リネームしない。

## 3. PR・コミット

両方ともConventional Commits形式：`種類(対象): 変更内容`。対象を短い英語で示し、変更内容は日本語でもよい。

```text
feat(studio): 共通編集画面を追加
fix(ui): スキル詳細表示の不具合を修正
refactor(ui): レイアウト設定を分離
docs(combat): 状態異常仕様を整理
chore(repo): 開発運用規則を統一
```

PR本文には以下を最低限記載する。

1. 目的。
2. 変更内容。
3. 変更しない範囲。
4. テスト・検証結果（実行コマンド・条件・成功／失敗）。
5. 未確認事項・残課題。
6. 関連する仕様書。

試験未実施を成功としない。AI試験・ブラウザエミュレーション・実機・聴感を区別する。PRの目的が変わったら、タイトルと本文を最終差分に合わせて更新する。

## 4. ソース命名

| 対象 | 規則・例 |
|---|---|
| 一般のJS/TSファイル | kebab-case：`skill-tooltip.js`、`layout-config.ts` |
| Reactコンポーネント | シンボル名はPascalCase。コンポーネント実装ファイルは一般ファイル規則の例外として`SkillPanel.tsx`等のPascalCase |
| 変数・関数 | camelCase：`selectedSkill`、`showSkillDetail` |
| 型・クラス | PascalCase：`SkillConfig`、`PreviewSession` |
| 定数 | UPPER_SNAKE_CASE：`MAX_SKILL_COUNT`。変更されない設定定数に適用し、すべてのconst変数を大文字にしない |
| CSSクラス | kebab-case：`skill-tooltip` |
| CSSカスタムプロパティ | 用途別プレフィックス付きkebab-case：`--ui-panel-gap`、`--fx-impact-scale`、`--story-fade-duration` |
| スキル・ボス等の内部ID | 既存snake_case等を維持：`heavy_slash`、`boss_knight_defense` |
| JSON設定ファイル | kebab-case：`slash-heavy.json` |

既存のファイル・関数・定数・CSS・IDを今回一括リネームしない。既存ID、設定JSON、セーブ形式、テストとの互換性を優先する。新規・変更対象への適用範囲をPRで説明する。
この規則はReact導入や本編移行の実施許可ではない。

既存素材は今回リネームしない。外部素材は出典・ライセンス・加工／再配布可否を確認する。購入素材・非公開素材・秘密情報は公開しない。
`private-assets/`などの除外設定が実際に有効か確認し、除外されていると推測しない。設定JSONに素材本体や秘密情報を埋め込まない。

## 6. 役割分担・標準フロー・Git操作の承認（2026-11-11更新）

### 6.1 三者の役割とGitHubの位置づけ

| 担当 | 責任 |
|---|---|
| ユーザー（プロジェクトオーナー） | 仕様・優先順位・ゲーム体験の最終判断、作業依頼の承認、GitHub操作と公開の最終承認 |
| ChatGPT（チャッピー） | GitHubの正本と最新の明示承認に基づく仕様相談・設計・受入条件整理、Codex依頼文作成、GitHubの実差分・PRレビュー、修正指摘の整理 |
| Codex | 承認された範囲での実装・文書変更・テスト・検証。作業依頼の承認に基づき、未コミット・未pushの指定がなければ対象ファイルだけをcommit・専用ブランチへpushし、コミットSHAと検証結果を報告 |
| GitHub | コード・設計資料の正本、変更履歴、三者のレビュー用成果物の共有基盤。ZIPでの受け渡しは原則必須としない |

ChatGPTが直接GitHub変更やPR操作を担当する場合も、Codexと同じく**その作業で承認された対象・操作の範囲**を守る。Codex完了報告は実変更の確認に代わらない。

### 6.2 標準作業フロー

1. **仕様相談と作業範囲の決定（ユーザー＋ChatGPT）**：対象機能、確定／暫定／検証中の区別、既存仕様との関係、受入条件を確認する。
2. **依頼文の作成・承認（ChatGPT→ユーザー）**：変更対象、禁止事項、検証内容、作業ブランチ、許可するGit操作を明記する。ユーザーが依頼単位で承認する。
3. **安全確認（Codex）**：最新リモートmain、既存ブランチ・PR、未コミット／未追跡差分を確認。競合のおそれがある場合は独立worktreeを利用し、勝手に既存成果を移動・削除しない。
4. **実装・資料更新と検証（Codex）**：承認範囲だけ変更し、必要なテスト・チェックを実施する。結果と未確認事項を記録する。
5. **レビュー用のGitHub共有（Codex、標準工程）**：承認された作業依頼では、特段の指定がなければ対象変更のcommit・専用ブランチへのpushまで承認されたものとし、都度確認せず実施する。未コミット・未pushの指定があれば、その指定を優先する。対象ファイルだけをcommitし、専用ブランチへpushする。ブランチURL・コミットSHA・ファイル一覧・テスト結果・既知の課題を報告する。**このpushはPR作成・マージ・公開の承認を意味しない。**
6. **実差分レビュー（ChatGPT＋ユーザー）**：ChatGPTがGitHub上の実ファイル、比較差分、テスト／CI、保護対象の状態を確認し、仕様との整合性と品質をレビューする。**Codex報告／ChatGPT直接確認／未確認**を分けて報告する。
7. **必要な修正（ChatGPT→ユーザー→Codex）**：指摘を整理し、ユーザー承認後に同じ作業ブランチで修正する。修正依頼の承認にも同じcommit・pushの標準規則を適用し、個別の制限指定を優先する。再push後は最終差分を再レビューする。
8. **PR作成（別途承認後）**：ユーザーがPR作成を許可した場合、承認された担当者が専用ブランチからPRを作成する。ChatGPTは最新base・最終HEAD・ファイル範囲・検証結果を確認する。
9. **マージ（別途明示承認後）**：ユーザーが対象PRのマージを許可した場合に実行する。マージ直前に最新baseとHEAD、競合・チェック・公開への影響を再確認する。
10. **反映確認・進捗記録**：mainのマージコミットと反映ファイルを確認し、必要に応じて公開URLで確認する。進捗・仕様状態は該当する`docs/status.md`や機能別正本に反映し、未反映事項を残す。ブランチ削除は別途承認を得る。

**基本線は「相談 → 依頼文承認 → Codex作業 → 許可されたブランチcommit／push → ChatGPT実差分レビュー → 修正 → PR作成承認 → PR最終レビュー → マージ承認 → 反映確認」。** commit・専用ブランチへのpushは作業依頼の承認に含む恒久的な標準工程とする。PR作成以降など、それ以外の操作は別途承認された範囲でのみ実行する。

### 6.3 承認の境界

| 操作 | 必要な承認 |
|---|---|
| 読み取り専用の調査・レビュー | 原則として実施可能 |
| ファイル修正、ブランチ作成・切替 | 対象と作業範囲の承認。既存差分に衝突する場合は停止して報告 |
| commit・専用ブランチへのpush | ユーザーによるCodex作業依頼の承認に含む。特段の指定がなければ都度確認は不要。未コミット・未pushの指定を優先する |
| PR作成 | 原則としてレビュー後に、対象PR／ブランチについて別途承認 |
| PRマージ | **対象PRごとに明示承認**。承認されたPRのHEADが変更された場合は差分を再レビュー |
| deploy、公開設定変更、main直接push | 影響と対象を説明して別途明示承認 |
| 既存PRのクローズ、ブランチ削除・リネーム | 個別の明示承認 |

**恒久的な標準規則**として、ユーザーがCodex作業依頼を承認した場合、特段の指定がなければその対象変更のcommit・専用ブランチへのpushまで承認されたものとする。都度確認は原則不要。ただし未コミット・未pushの指定を必ず優先し、対象外の変更や別作業まで承認を拡張しない。PR作成、マージ、デプロイの許可は別操作として扱う。予期せぬ差分・失敗テスト・秘密情報の混入があれば、承認済みでも停止して報告する。

commit前に差分とstatusを確認し、対象パスだけをステージングする。未コミット研究や購入素材を含める包括的な`git add .`を避ける。push前にリモートURL、対象ブランチ、コミットSHA、差分を確認する。強制pushは禁止。

### 6.4 並行作業・未コミット成果の保護

異なるブランチでも、同じworktreeで作業すれば未コミット差分が自動的に隔離されるわけではない。並行作業では独立worktreeを原則検討する。
STEP 3-B①の未コミット成果、独立研究、非公開素材、FX Lab PR #1などは保護対象。既存ファイルを独断で移動・削除・stash・reset・上書きしない。独立worktreeを使っても後のマージで衝突することはあるため、PRの目的を分けて最新mainとの差分を確認する。

### 6.5 Pagesへの影響

[公開方式](architecture.md)はGitHub側でも確認する。2026-11-11確認時点ではGitHub Pagesのlegacy方式、**mainブランチのルート（/）から自動公開**。
したがってmainへのマージは公開への影響を伴う操作であり、単なるローカル整理ではない。マージだけ許可されていて公開の意図が不明なら、先にその影響を確認する。
公開時は対象SHAのジョブ成功、公開URLの新HTML/JS/CSS、必要な画像・音源、キャッシュを確認する。ジョブ成功と公開版の操作検証は別に報告する。失敗や未確認を公開完了と扱わない。

## 7. 仕様・研究・成果物の保護

- 最新ユーザー承認を最優先し、仕様状態と実装状態は[入口の定義](README.md)で管理する。
- 本編と研究環境を混同せず、研究結果を自動的に正式仕様へ昇格させない。
- 未コミット・未追跡の研究成果、検証データ、他の作業差分を保護する。
- 既存FX Labの[PR #1](https://github.com/elizabeeeth555/roguelike-card-game/pull/1)を保護する。王座工房の参考／移植元であり、統合を自動実行しない。
- 購入・非公開素材・秘密情報を公開しない。GitHub Pagesでの配信対象も確認する。
- ゲームロジックとUIを原則別PRにし、独立研究には研究用の設定と成果物保存先を用意する。
- 文書整理で旧資料を削除する場合は固有情報の移管を確認する。歴史的レポートを最新状態へ書き換えない。

## 仕様の単一正本管理

仕様項目ごとに正本を一つ定め、他の現行資料はMarkdownリンクで参照する。要約・進捗・編成一覧は置けるが、個別の数値・効果・条件を再定義しない。過去の研究報告・履歴は当時の条件を保持し、現行の正本と区別する。

| 管理元 | 所有する仕様 |
|---|---|
| [スキル](features/skills.md) | 全スキルの名称・ID・効果・MP・CD・条件・タグ・個別強化・奥義個別仕様。実装済み／予定／研究／保留／廃止を含む。スキル固有UI・素材設定の管理元もここに記録 |
| [戦闘](features/combat.md) | 毒・バリア・CD等の共通処理、共通計算順序 |
| [ボス](features/bosses.md) | ボス固有能力・ギミック・編成。通常スキルの個別定義は所有しない |
| [進行](features/progression.md) | 編成枠、世代進行、解放・強化予算、保存の共通方針 |
| [UI](features/ui.md) | 共通表示・操作・演出方針 |
| [世界観・素材](features/world-assets.md) | 世界観、共通素材方針、出典・権利と実ファイルの確認 |

上記以外も、変更前に管理元を一つ定める。正本から実装・設定ファイルを参照できるが、資料とコードの責務を混同しない。承認済みであることと実装済みであることは別軸で記録する。状態・優先順位の定義は[資料入口](README.md)を参照する。

新規追加・変更・廃止では、対象正本の該当項目と根拠・状態を更新し、参照元・旧定義・ID互換性を確認する。実装変更時も同時に必要な資料更新、コードとの照合、重複定義の検索、Markdownリンク検証を行う。個別UI・素材が別の設定ファイルに実装される場合は、その参照先と管理責任を正本へ記録し、素材本体や秘密情報を転記しない。

移管時は元の効果・数値・注意事項の欠落がないことを比較し、未承認案を確定へ昇格させない。履歴や研究成果は書き換えず、現行資料の重複をリンクへ置き換える。廃止した仕様は廃止・置換先を明示する。

承認の原文が不足するなど、正本へ反映できていない事項は[status](status.md)へ根拠・不足内容・次の確認を記録し、完了扱いにしない。推測で穴埋めせず、確認後に正本と参照元を再検証する。本規約はGit操作の承認範囲を拡大しない。
